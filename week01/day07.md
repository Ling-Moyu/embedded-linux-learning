## gdb 六个核心命令

| 命令                  | 作用             |
| ------------------- | -------------- |
| `l` (list)          | 显示源代码          |
| `b 行号` (breakpoint) | 设断点，程序跑到这行暂停   |
| `r` (run)           | 运行，碰到断点停下      |
| `n` (next)          | 执行下一行（不进入函数内部） |
| `s` (step)          | 执行下一行（进入函数内部）  |
| `p 变量` (print)      | 打印变量当前值        |

辅助：`c`（continue 继续跑）、`bt`（backtrace 看调用栈）、`info b`（看所有断点）、`delete N`（删断点，不带数字删全部）。

## 两个关键规矩（不搞懂会一直懵）

1. **停在某一行的意思是"这行即将执行，但还没执行"**
   - 断点停在 `int sum = sum_to(n);` 时 `p sum` 显示 0——因为赋值还没发生
   - 要先 `n` 执行过这一行，变量才有值
2. **gdb 遵守 C 的作用域**
   - 在 `sum_to` 函数里 `p avg` 会报 `No symbol "avg" in current context`
   - 局部变量只在它自己的函数里可见，就像在厨房问客厅的电视开没开

## 调试逻辑 bug 的标准流程（今天的核心收获）

> 设断点 → 单步走 → 每步打印变量 → **变量值和预期第一次出现偏差的那一行，就是案发现场**

今天实战：`sum / n` 是 int ÷ int，结果还是 int，小数直接砍掉，除完才赋给 float——所以 `10/4` 得到 2 而不是 2.5。修法：`float avg = (float)sum / n;` 强制先把 sum 转成 float 再除。

这种"不崩但算错"的 bug 比崩溃难抓十倍，盯着代码干瞪眼效率极低，gdb 单步是唯一高效手段。

## 三个亲手制造的真事故（最值钱的部分）

### 事故 1：OBJS 混进源文件，clean 删掉了源代码

```makefile
OBJS = bug.c        # ❌ OBJS 应该放 .o 编译产物，我放了 .c 源文件
clean:
	rm -f $(OBJS) $(TARGET)    # 展开后 = rm -f bug.c bug → 源码没了！
```

报错 `make: *** No rule to make target 'bug.c', needed by 'bug'. Stop.` 的意思是：你让我造 bug，它依赖 bug.c，但 bug.c 不存在，我也没有任何规则能生成它。

**教训**：

- `make clean` 只该删编译产物，**源代码永远不进删除列表**
- 这就是 git/仓库存在的意义——推过 GitHub 十秒恢复，没推只能重敲

### 事故 2：make 默认执行"第一条规则"

光杆 `make` 永远执行 Makefile 里**第一条规则**。规则顺序乱了（clean 跑到了前面），make 就去执行删除而不是编译。

### 事故 3：`%0: %c` —— 字母 o 写成数字 0（差点发生）

模板规则里如果写成数字 0，永远匹配不上 `conv.o`（o 是字母）。更隐蔽的是 make 会悄悄用内建隐含规则兜底，**程序照样能编，但 `-Wall -g` 全部静默丢失**——make 不会因为规则写错而报错，它只会默默用别的规则。

**对策**：make 每次执行前会 echo 展开后的命令，**盯住这个"对账单"确认 `-Wall -g` 都在**。

## C 语言知识点

- **`argc / argv`**：命令行参数入口。`./hexconv 13` 时 argc=2，argv[0]="./hexconv"，argv[1]="13"（全是字符串）
- **`atoi`**：ASCII to integer，字符串 "13" → 数字 13，需要 `#include <stdlib.h>`
- **`'0' + 余数`**：数字转字符的惯用把戏，字符 '0' 的 ASCII 码加 3 就是 '3'（单片机串口打印数字天天用）
- **`idx++` 后置自增**：先用当前值，用完再加 1。`buf[idx++]` 第一圈写的是 buf[0] 不是 buf[1]；`++idx` 前置才是先加再用
- **整数除法陷阱**：`int / int = int`，小数部分直接砍掉

## 反序 bug 的原理与修复

`to_binary` 用"除 2 取余"：第一次得到的余数是**最低位**，却写进了 buf[0]（最前面）——整个字符串变成"低位在前"，读出来就是反的。

修复：双指针原地反转——

```c
int left = 0, right = idx - 1;
while (left < right) {
    char tmp = buf[left];
    buf[left] = buf[right];
    buf[right] = tmp;
    left++;
    right--;
}
```

## 测试设计的教训：回文测试用例

- `./hexconv 255` 输出 11111111——正着倒着一样（回文），**抓不到反序 bug**
- `./hexconv 13` 输出 1101——对称性差，当场暴露 bug
- **测试用例要专挑"对称性差"的输入**，特殊值（0）和普通值都要测

## Makefile 增量编译的兑现时刻

只改 conv.c 后 make，输出只有两条命令：重编 conv.o + 链接，main.o 没动——"只重编变过的东西"第一次真实发生，这就是 Makefile 的本质价值。

## 一句话总结

程序崩溃用 `bt` 看现场；程序算错不断点单步看变量——**gdb 让你从"猜 bug"变成"看 bug"**。
